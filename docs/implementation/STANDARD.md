# 实施文档规范

## 目标读者与职责

实施文档面向直接编写、评审和维护代码的开发者，把已经确认的详细设计展开为可以逐项照做的代码实施蓝图。开发者不需要重新判断架构是否采用另一种方案，只需要在开始编码前检查文档是否存在逻辑矛盾、流程阻塞、无法实施或相互冲突的指令；没有此类缺陷时必须直接按照文档实现。

实施文档不得重新设计详细设计已经确定的架构、技术、模块职责、代码行为和业务结果。它负责把这些决策映射到具体文件与符号、接口实现、数据结构、组件实现、控制流程、异常传播、迁移步骤和验证操作。确实缺少必要决策时必须返回详细设计，不得由实施文档自行选择。

## 元数据

主实施文档：

```yaml
---
schema_version: 1
document_type: implementation
id: IMP-DOM-001
title: 示例功能实施
status: 草案 | 可开发 | 实施中 | 已完成 | 已废弃
relations:
  detailed_design:
    - id: DOM-001
      path: ../detailed-design/example.md
---
```

子实施文档：

```yaml
---
schema_version: 1
document_type: implementation
id: IMP-DOM-001A
title: 子主题
status: 实施中
relations:
  implementation_parent:
    - id: IMP-DOM-001
      path: ../example.md
---
```

主实施文档标识格式为 `IMP-<领域码>-NNN`，领域码由至少三个大写英文字母组成；子实施文档在主标识后增加一个大写英文字母，例如 `IMP-AIM-001`、`IMP-AIM-001A` 和 `IMP-AUTH-001`。

- 主实施文档必须关联至少一个详细设计，并通过详细设计追溯到总体设计，避免重复维护跨级关系。
- 子实施文档必须关联且只关联一个主实施文档，并与主文档保持相同状态。
- 主文档必须通过 `implementation_children` 反向列出全部子文档。
- 只有主实施文档进入 `INDEX.md`；子文档通过主文档导航。
- 可以使用可选的 `code_roots` 字符串数组记录稳定的代码目录；具体文件映射仍写在正文中。

## 必需内容

- 目标与范围。
- 详细设计逐项落实。
- 技术约束与非目标。
- 代码结构与模块落位。
- 接口实现契约。
- 数据实现。
- 数据获取、运行时所有权、分发、生命周期与失效刷新。
- 组件实现。
- 控制流程。
- 权限与安全。
- 状态一致性、事务与并发。
- 代码边界。
- 技术异常处理。
- 外部依赖。
- 性能与资源限制。
- 日志、监控与脱敏。
- 迁移、兼容与回滚。
- 验证方案。
- 实施顺序与完成条件。

复杂实施文档可以拆分子文档。主文档必须保留完整导航和整体约束，子文档可以承载具体章节。不适用的内容必须明确说明原因。

## 详细设计逐项落实

逐项落实用于证明实施蓝图完整执行详细设计，不要求每个设计条目对应一个独立代码结构，但不得遗漏或重新解释：

| 详细设计条目 | 具体代码落位 | 实施章节 | 验证方式 |
| ------------ | ------------ | -------- | -------- |

## 继承详细设计前置条件

实施文档不得重新声明、验证或处理详细设计的前置条件。所有实施步骤均从前置条件已经满足的位置开始，不得为其增加获取、校验、重试、兜底、默认值、跳转、恢复或捕获分支，也不得把违反前置条件列入当前实施的技术异常和验证方案。

前置条件在运行时被违反时，当前代码应让失败自然上抛，不做专用转换。现有统一顶层错误边界可以按其自身实施文档工作，但本实施文档不得为此前置条件设计额外行为。若实施者发现前置条件没有实际保证方，必须把它作为详细设计缺陷报告，不能在当前实现中补救。

## 实施职责与跨模块边界

实施文档只能展开当前文档所属模块的文件、符号、接口实现、数据实现、组件和控制流程。它可以说明如何消费其他模块已经生效的公开契约，但不得要求修改其他模块的文件、复制其他模块逻辑、访问其他模块内部数据，或者替其他模块决定实现方案。

实施过程中发现其他模块必须变更时，必须停止当前实施，在会话中报告目标模块、所需能力、阻塞原因和影响范围。用户确认后切换到目标模块，先更新并确认目标模块的详细设计，再更新其实施文档和代码；目标模块完成后才能返回当前实施。不得在当前实施文档中记录临时变更请求或先写跨模块代码。

## 数据获取、所有权与流转

实施文档必须把详细设计的数据方向展开为可以直接编码和评审的运行时契约。不得只写“由父组件管理”“通过 context 共享”“请求后刷新”或“使用 store”，而不说明具体提供者、消费者、写入入口和刷新范围。

每类运行时数据至少记录：

| 数据项 | 权威来源 | 获取或创建位置 | 唯一运行时 owner | 分发方式与消费者 | 允许的写入入口 | 生命周期与清理 | 失效与刷新 |
| ------ | -------- | -------------- | ---------------- | ---------------- | -------------- | -------------- | ---------- |

并遵守以下要求：

- 区分持久化事实、接口请求结果、路由状态、表单草稿、派生值和缓存；同一份数据不得存在多个未定义优先级的可写 owner。
- 请求数据必须说明谁拥有 data、loading、error、空值和陈旧结果；消费组件默认只读，通过显式 action、emit、命令或路由变更发起修改。
- props、provide/inject、路由、store、缓存、事件或消息必须说明选择理由和边界。使用 provide/inject 时必须画出或写明 provider 与消费者的祖先关系；路由组件消费注入值时，承载该组件的 `RouterView` 必须位于 provider 子树内。
- 派生值必须说明输入及重算位置；复制和缓存必须说明创建、失效、清理和并发覆盖规则。没有明确理由时不得建立第二可写副本或重复请求相同事实。
- 组件卸载、路由切换、用户切换、请求竞态和敏感数据使用结束时的清理责任必须明确。

所有 mutation 还必须具有逐项失效契约：

| 操作 | 持久化写入点 | 成功后失效的数据 | 重取或局部更新动作 | 路由、选择或草稿修正 | 失败时保留内容 |
| ---- | ------------ | ---------------- | ------------------ | -------------------- | -------------- |

不能用“刷新全部”代替分析，除非文档说明全部数据确实失效且成本可接受；也不能漏掉由展示名称、计数、关联关系等派生出的间接失效数据。简单功能确实没有跨边界数据时，仍须在“数据实现”中明确写出不适用原因。

## 范围取舍、主动阻断与涌现能力

实施文档中的技术非目标表示本次不建设、不验证或不维护某项技术能力，不代表必须保证该能力不可用。不得仅因详细设计将某项能力标记为“暂不提供”“范围外”或“不保证兼容”，就增加识别、拒绝、破坏、反适配或其他主动阻断逻辑。

主动阻断必须能够追溯到以下依据之一：

- 详细设计明确规定的禁止性业务行为及用户可见结果；
- 实现已设计能力所必需的接口、类型、数据、安全或资源边界，且不会产生详细设计未规定的新业务结果。

技术边界如果会产生新的用户可见拒绝结果，必须停止实施设计并先返回详细设计补充业务边界。不得以“确保范围外能力不可用”为技术目标。

不可预测的涌现能力不需要在实施文档中列举或建立追溯关系。不得为稳定它而增加专用代码、兼容层、迁移或专项测试，也不得为了消除它而增加破坏逻辑。正常实现和重构只需保证正式文档规定的契约。发现涌现能力带来安全、合规、隐私或数据一致性风险时，必须先报告并取得文档决策，不能直接封堵。

## 代码边界与技术异常

代码边界建议按下表表达：

| 技术边界 | 检测位置 | 处理或忽略方式 | 依据 | 验证 |
| -------- | -------- | -------------- | ---- | ---- |

技术异常建议按下表表达：

| 技术情况 | 传播或转换 | 状态一致性 | 重试或回滚 | 日志监控 | 验证 |
| -------- | ---------- | ---------- | ---------- | -------- | ---- |

实施文档必须说明当前实现负责的技术情况如何处理以及依据。不得因详细设计使用“业务异常”一词就机械创建程序异常，也不得把详细设计前置条件不满足纳入当前技术异常处理。

## 专业图表

实施文档应优先使用专业技术图表表达代码结构、控制流程和实现边界。只有功能模块比较简单，并且文字描述比图表更简洁、清晰时，才可以省略图表。可以使用的图表包括：

| 图表类型         | 适用场景                                 | Markdown 表达方式         |
| ---------------- | ---------------------------------------- | ------------------------- |
| 系统上下文图     | 表达系统与用户、外部系统和技术依赖的关系 | Mermaid `flowchart`       |
| 运行单元关系图   | 展示 Web、服务、数据库、队列等运行单元   | Mermaid `flowchart`       |
| 模块依赖图       | 明确代码模块的职责、依赖和调用方向       | Mermaid `flowchart`       |
| 接口时序图       | 多个组件按时间顺序协作                   | Mermaid `sequenceDiagram` |
| 技术流程图       | 校验、算法、分支或处理步骤较复杂         | Mermaid `flowchart`       |
| 技术状态机图     | 协议、任务或资源具有内部技术状态及转换   | Mermaid `stateDiagram-v2` |
| 数据流图         | 数据经过多个组件、存储或信任边界         | Mermaid `flowchart`       |
| ER 图            | 涉及多张数据表、关系、约束或所有权       | Mermaid `erDiagram`       |
| 类型或类关系图   | 接口、类型、继承或组合关系复杂           | Mermaid `classDiagram`    |
| 信任边界图       | 涉及鉴权、敏感数据、外部输入或安全区域   | Mermaid `flowchart` 子图  |
| 认证授权流程图   | 登录、令牌、会话或权限判断流程复杂       | Mermaid `sequenceDiagram` |
| 事务边界图       | 一次操作跨越多个写入、锁或一致性边界     | Mermaid `sequenceDiagram` |
| 并发时序图       | 存在竞态、幂等、锁、版本检查或并行任务   | Mermaid `sequenceDiagram` |
| 事件与消息流图   | 使用事件、队列、订阅、异步任务或补偿操作 | Mermaid `sequenceDiagram` |
| 错误传播图       | 技术错误经过多层传播、转换、聚合或屏蔽   | Mermaid `flowchart`       |
| 超时与重试图     | 存在超时、重试、退避、熔断或最终失败     | Mermaid `sequenceDiagram` |
| 缓存生命周期图   | 涉及缓存写入、失效、刷新或一致性         | Mermaid `stateDiagram-v2` |
| 数据迁移图       | 展示数据转换、校验、切换和回滚           | Mermaid `flowchart`       |
| 可观测性数据流图 | 日志、指标、链路和告警经过多个组件       | Mermaid `flowchart`       |
| 资源生命周期图   | 文件、连接、任务或临时资源需要创建和释放 | Mermaid `stateDiagram-v2` |
| 构建发布流程图   | 功能涉及特殊构建、部署、发布或回滚过程   | Mermaid `flowchart`       |

跨模块调用、异步流程、并发控制、事务一致性、复杂状态迁移或安全信任边界仅靠文字难以唯一确定实现时，相关图表是该实施文档达到可开发状态的必要内容。图表必须与接口实现、数据实现、代码边界和技术异常处理一致，但不得因为绘制技术流程而改变详细设计规定的方案和结果。

## 方案质量与阻断

实施文档必须忠实展开详细设计，不得以优化、惯例或个人偏好为由替换已经确定的方案。实施文档作者和开发者只审查逻辑矛盾、流程阻塞、缺少必要信息、无法实施以及会不可避免地产生明显性能、维护、安全或一致性问题的内容。

发现上述问题时必须停止并按 [治理规范](../GOVERNANCE.md#缺陷阻断与上报) 报告详细设计缺陷，不得强行实现、擅自偏离或在实施文档中暗自重新设计。没有阻断问题时，应采用清晰、直接、与仓库惯例一致的方式执行文档，不制造文档未要求的抽象或分支。

## 可开发条件

进入 `可开发` 或 `实施中` 前必须确认：

- 所有关联详细设计均为 `已确认`；
- 详细设计的业务、架构、技术和代码行为要求均被逐项落实且没有重新设计；
- 详细设计的前置条件没有被重复验证、处理或加入异常与测试分支；
- 当前实施只修改所属模块，依赖的其他模块能力已经生效，没有越界设计、跨模块文件修改或临时复制实现；
- 所有主动阻断均有有效的详细设计或必要技术边界依据，没有把范围取舍误实现为禁止；
- 文件与符号、接口、数据、组件、控制流程、权限、状态一致性、代码边界和技术异常足以让开发者直接编码；
- 每项运行时数据都有唯一 owner、只读分发和写入入口，每个 mutation 的失效与刷新范围已经逐项确定，provider 与消费者拓扑不存在歧义；
- 迁移、兼容、回滚和验证方案与风险相称；
- 没有已知的上游缺陷迫使实现采用明显低效、复杂、不安全或难以维护的方案。
