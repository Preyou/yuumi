# 开发文档治理规范

本文规定总体设计、详细设计、实施文档与代码之间的依赖、状态、变更顺序和追溯要求。各层文档的具体内容要求与模板由对应目录中的 `STANDARD.md` 和 `TEMPLATE.md` 规定。

## 文档层级

```text
总体设计 -> 详细设计 -> 实施文档 -> 代码
```

- [总体设计规范](./overall-design/STANDARD.md)
- [详细设计规范](./detailed-design/STANDARD.md)
- [实施文档规范](./implementation/STANDARD.md)

总体设计决定产品范围。详细设计面向架构师及方案评审者，在总体设计范围内同时确定业务行为、架构方案、技术约束和必须满足的代码行为。实施文档面向直接编码的开发者，将详细设计展开为可以逐项照做的代码实施蓝图，不再重新选择架构或改变技术决策。

上游决定下游允许表达的范围和已经确定的决策。下游可以补充本层所需的落地细节，但不得增加、遗漏、改变或重新解释上游内容。

## 文档内容维护

Markdown（`.md`）视为代码文件，统一遵循[代码格式化与变更验证规则](../.ai/rules/30-change-validation.md)。

文档描述当前有效的目标状态，不承担功能变更日志的职责。功能、接口、组件或实现机制被移除后，直接删除对应描述，并同步清理失效的索引、关联和图表节点；不保留“已移除”“禁止调用旧功能”“不得恢复旧实现”等遗留说明。历史变更通过版本控制追溯。

## 前置条件

前置条件是在当前功能或模块开始之前，已经由其他责任方保证成立的事实。前置条件只在详细设计中声明；实施文档和代码直接假设它们已经满足，不重复声明处理流程，也不为不满足的情况增加验证、获取、重试、兜底、默认值、跳转、恢复或捕获逻辑。

详细设计声明前置条件时必须指出保证方或关联设计。只有确实由上游入口、其他模块或外部契约负责建立并保证的条件，才能作为前置条件；当前模块自己负责验证的外部输入、权限、安全边界或业务状态不能改称前置条件来逃避处理责任。

前置条件不满足表示上游契约或系统集成存在缺陷，不属于当前功能的业务异常或技术异常。当前实现不得捕获并转换该问题，应让失败自然上抛；仓库已有的统一顶层错误边界可以按其自身文档处理，但当前模块不得为此前置条件增加专用分支。

前置条件的建立、失败结果和验证由保证方的详细设计、实施文档和测试负责。消费方的设计、实施和测试均从前置条件已满足的位置开始。如果找不到能够提供该保证的上游设计，当前详细设计存在缺陷，不得继续编写实施文档。

## 模块职责与跨模块变更

每份详细设计和实施文档只能设计、展开和验证其声明范围内的模块职责。当前模块可以说明自己需要其他模块提供什么边界能力或保证，但不得替其他模块规定功能行为、内部架构、技术方案、数据结构、异常处理、文件修改或代码实现。

设计或实施当前模块时，如果发现必须扩展其他模块，必须立即停止受影响范围并在当前会话中向用户提出变更请求。请求只说明：

- 需要变更的目标模块；
- 当前模块需要目标模块提供的能力或保证；
- 当前工作为什么无法继续；
- 受影响的文档或代码范围。

变更请求不得替目标模块给出正式设计，不写入当前模块的正式文档，也不要求新增固定的“跨模块变更请求”章节、元数据或索引项。会话只用于报告阻塞和取得用户决策，不能替代目标模块的正式设计。

用户确认变更后，必须切换到目标模块，按照该模块自己的总体设计（需要时）、详细设计、实施文档和代码顺序完成变更。目标模块形成有效保证后，才能返回当前模块，将其作为依赖或前置条件继续工作。用户拒绝变更时，当前范围保持阻塞，或者先修改当前模块的详细设计以消除该依赖。

当前模块不得以临时适配、兼容兜底、复制逻辑、直接访问其他模块内部数据、修改其他模块文件或先行假设未来契约等方式绕过这一门禁。一个变更可以包含多个模块的文档和代码，但每份文档仍只负责自己的模块，跨模块协调不改变职责归属。

## 数据流设计门禁

设计中的“数据”不仅指数据库记录，也包括接口响应、路由状态、表单草稿、派生值、缓存、上下文注入值、事件和消息。凡是数据跨越模块、组件、路由、进程、存储或信任边界，必须在编码前预定其流向，不能留给实现阶段凭惯例决定。

详细设计负责确定架构层面的数据契约：权威来源、产生或维护数据的责任模块、消费模块、允许的读写方向，以及一致性、生命周期和安全边界。详细设计不展开具体变量和函数，但必须足以排除相互冲突的数据来源、循环依赖、越权写入和无法确定责任方的方案。

实施文档必须进一步锁定每类运行时数据的：

- 获取或创建位置与唯一运行时 owner；
- 只读分发方式、消费者和允许的写入入口；
- 派生、复制、缓存以及加载、错误、空值和陈旧状态的归属；
- 生命周期、清理时机、并发覆盖规则；
- 每个 mutation 成功后的失效集合、刷新方式、路由或选择状态修正；
- 敏感数据跨边界时的最小暴露与销毁要求。

使用 props、provide/inject、路由出口、store、缓存、事件或消息时，实施文档必须写明提供者与消费者的运行拓扑。依赖祖先关系的注入不得只列组件名称；必须明确 provider 包含对应消费者或路由出口。重复获取、多个可写副本和多级缓存只有在文档明确责任与一致性策略时才允许。

如果任何数据的权威来源、owner、写入入口、分发路径或失效规则无法唯一确定，文档视为存在阻断缺陷，不得进入下一层。自动检查只验证可确定的结构要求；数据流是否完整、一致并可实施由文档评审和代码评审逐项核对。

## 设计范围、禁止与涌现能力

设计文档只规定有意设计的产品能力、明确的范围取舍和明确禁止的行为。以下概念不得混淆：

| 分类             | 含义                                 | 下游义务                                                     |
| ---------------- | ------------------------------------ | ------------------------------------------------------------ |
| 已设计能力       | 产品明确承诺提供的能力               | 必须完整实现、验证并保持契约                                 |
| 暂不提供或范围外 | 本期不建设专用能力，不承诺交付       | 不实现专用能力，也不得据此增加主动阻断                       |
| 不保证兼容       | 未专项验证、测试或维护，可能偶然可用 | 不承诺稳定性，不得为了确保不可用而主动破坏                   |
| 明确禁止         | 因业务、安全或合规原因不允许发生     | 必须由详细设计规定可观察的拒绝结果，实施文档才能设计阻断机制 |

“不支持”含义不明确，不得单独作为范围或行为要求使用；必须改写为“暂不提供”“不保证兼容”或具有明确结果的“禁止”。范围外、不提供和不保证均不等于禁止，不能推出检测、拒绝、破坏或限制该用途的实现要求。

由已设计的通用能力自然组合产生的不可预测用途属于非承诺的涌现能力。涌现能力不是独立设计的产品能力，不要求在总体设计、详细设计、实施文档或索引中识别、列举或追踪；未记录不代表禁止。代码不得专门维持或破坏此类用途，也不需要为其增加兼容层、迁移、专用分支或专项测试。正常变更只需保持正式文档规定的行为，涌现能力随实现变化不构成设计违约。

涌现能力只有在决定正式支持、决定明确禁止，或者发现安全、合规、隐私、数据一致性等风险时才进入文档流程：正式支持时按总体设计、详细设计、实施文档和代码的顺序纳入；明确禁止时先由详细设计规定禁止原因及用户可见结果；发现风险但尚无决策时必须停止受影响范围并报告用户，不得直接在代码中封堵。

“代码不得增加未设计行为”是指不得有意增加未设计的产品能力，不要求穷举或消除已设计通用能力自然产生的所有组合用途。

## 元数据

正式设计文档必须以 YAML Front Matter 声明元数据。元数据是文档标识、类型、标题、状态及上下游关系的唯一事实来源；正文和索引不得独立维护另一份状态或关系事实。

公共必填字段：

```yaml
---
schema_version: 1
document_type: overall-design | detailed-design | implementation
id: <稳定标识>
title: <不含标识的标题>
status: <该文档类型允许的状态>
relations: {}
---
```

约束：

- `schema_version` 当前固定为数字 `1`。
- `id` 在所有正式设计文档中全局唯一，创建后不得因改名而改变。
- 一级标题必须为 `# <id> <title>`，并与元数据一致。
- 关系项必须同时记录目标 `id` 和相对当前文档的 `path`。
- 双向关系必须对称；父子实施文档只通过 `implementation_parent` 与 `implementation_children` 互相关联。
- `README.md`、`INDEX.md`、`STANDARD.md`、`TEMPLATE.md` 和本文不是产品设计文档，不使用上述元数据。

允许的关系键：

- `overall_design`
- `detailed_design`
- `implementation`
- `implementation_parent`
- `implementation_children`

## 状态

总体设计：

- `构想`：记录远期方向，不允许据此开发。
- `已规划`：进入交付范围，必须关联详细设计。
- `已废弃`：不再作为有效设计依据。

详细设计：

- `草案`
- `待确认`
- `已确认`
- `已废弃`

实施文档：

- `草案`
- `可开发`
- `实施中`
- `已完成`
- `已废弃`

只有完整且状态为 `已确认` 的详细设计可以进入实施设计。只有状态为 `可开发` 或 `实施中` 的主实施文档允许对应代码进入开发。子实施文档继承主实施文档的开发门禁，状态必须与主文档一致。

## 变更顺序

任何功能新增、调整、删除或行为修复都必须先更新文档，再更新代码：

```text
总体设计（需要时）
  -> 详细设计变更并确认
  -> 实施文档变更并生效
  -> 代码变更
```

- 实施文档变更超出详细设计时，必须先停止并修改、重新确认详细设计。
- 当前模块的设计或实施需要其他模块新增或改变能力时，必须停止当前范围并按“模块职责与跨模块变更”规则请求目标模块变更，不得在当前文档中越界设计。
- 详细设计变更超出总体设计的 `已规划` 范围时，必须先修改总体设计。
- 编码期间发现具体实施步骤需要改变时，必须停止编码并先更新实施文档；涉及详细设计已经确定的业务、前置条件、架构、技术、模块职责或代码行为时继续返回详细设计。
- 文档与代码可以在同一分支或 Pull Request 中，但不得改变实际工作顺序。

## 缺陷阻断与上报

下游工作因上游文档缺失、歧义、矛盾、不可验证或与现状冲突而无法唯一确定方案时，必须停止受影响范围并报告用户，不得自行假设、忽略或在代码层绕过。

如果遵守上游文档会不可避免地造成明显低效、难以维护、逻辑过度复杂、架构破坏、安全问题或数据一致性风险，也必须停止并报告：

- 造成问题的具体上游条目；
- 可预见的技术后果；
- 可行替代方案；
- 替代方案对业务行为或技术契约的影响；
- 需要用户决定的事项。

仅有个人风格偏好，或者仍存在合理、清晰、可维护的合规方案时，不构成阻断理由。

## 索引与追溯

- 每层 `INDEX.md` 只负责导航，内容必须与正式文档元数据一致。
- 总体设计索引的关系列必须显式列出详细设计标识；详细设计索引必须显式列出主实施文档标识；实施文档索引必须显式列出详细设计标识。多个关系必须逐项列出，不得使用“从某标识至某标识”的范围缩写。
- 总体设计与详细设计、详细设计与主实施文档必须双向关联。
- 子实施文档与主实施文档必须双向关联；子文档通过主文档继承详细设计关系。
- 详细设计可以记录架构决策所需的稳定模块、技术和代码行为；实施文档负责将其展开到具体文件、符号、控制流程和验证项。
- 索引、元数据与正文不一致时，文档不合规，不得进入下一阶段。

## 专业图表规范

设计文档应优先使用与所在层级和表达目标匹配的专业图表表达设计。只有功能模块比较简单，并且使用文字或表格比图表更简洁、清晰时，才可以省略图表。涉及多角色协作、复杂分支、状态迁移、跨模块调用、异步并发、数据流、信任边界或部署边界等情况时，不得仅以文字能够描述为由省略相应图表。

通用要求：

- 图表必须符合所在文档层级的职责，不得借图表绕过上游文档边界或引入未设计的行为。
- 每张图必须有名称，并说明用途或希望回答的问题；一张图只承担一个主要表达目标，内容过于复杂时应拆分。
- 图表属于文档内容的一部分，必须与元数据、正文、表格及其他图表一致。发生冲突时视为文档缺陷，受影响的下游工作必须停止。
- 关键规则、边界、异常结果和技术契约不得只存在于图形中，必须同时提供可检索、可评审的文字或表格说明。
- 默认使用 Markdown 表格或 Markdown 内嵌 Mermaid，以便版本控制和评审。各层规范中的推荐清单只列出适合以 Markdown 或 Mermaid 清晰维护的图表；需要自由画布或专用建模工具才能有效表达的图表不作为默认推荐。确有必要使用其他专业工具时，必须提交可编辑源文件，并以相对路径引用同仓库内的渲染文件；外部网页或不可编辑图片不得作为唯一来源。
- 图中的角色、状态、模块、接口和数据名称必须与正文一致；缩写、颜色或特殊符号必须提供图例或解释。
- 功能是否足够简单、文字是否比图表更简洁，以及图表语义是否正确，由人工评审判断。自动检查不得以图表数量推断文档完整性。

各层允许使用的图表类型、适用场景和表达边界由对应的 `STANDARD.md` 规定。

## 自动检查边界

自动检查负责确定性的结构问题：元数据格式、合法状态、唯一标识、标题、文件路径、关系对称性、索引一致性、必需章节与状态门禁。

自动检查不判断业务设计是否合理、技术方案是否优良、文字是否真正面向目标读者，也不通过篇幅或关键词数量推断内容完整性。这些内容由人工评审负责。
