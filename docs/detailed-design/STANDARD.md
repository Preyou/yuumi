# 详细设计规范

## 目标读者与职责

详细设计主要面向架构师、技术负责人和方案评审者。读者理解软件开发和常见技术概念，通常不直接依据本文逐行编码，而是审核业务行为、架构方案、模块职责、技术选择和代码行为要求是否合理、完整且可实施。

详细设计既定义业务行为、业务边界和业务异常，也可以规定架构、技术选型、模块边界、接口原则、数据原则、错误传播原则以及必须满足的具体代码行为。技术内容应服务于方案评审和下游实施约束，不要求展开到逐文件、逐函数的编码步骤。

业务异常表示偏离业务常态或需要区别对待的业务情况，可以只是正常操作产生的某种业务状态，不代表代码必须创建程序异常、错误码或专门分支。是否需要特定代码行为，可以由详细设计基于整体架构明确规定。

## 元数据

```yaml
---
schema_version: 1
document_type: detailed-design
id: DOM-001
title: 示例功能
status: 草案 | 待确认 | 已确认 | 已废弃
relations:
  overall_design:
    - id: OD-001
      path: ../overall-design/example.md
  implementation:
    - id: IMP-DOM-001
      path: ../implementation/example.md
---
```

详细设计标识格式为 `AAA-NNN`：`AAA` 是三位大写英文字母组成的领域码，`NNN` 是三位数字，例如 `AIM-001`。

- 除 `已废弃` 的历史文档外，必须关联一个有效总体设计。
- 尚未创建实施文档时可以不声明 `implementation`；实施文档创建后，双方必须立即建立对称关系。
- 详细设计不得包含 `code_roots` 或其他代码位置元数据。

## 必需内容

- 用户目标。
- 业务术语。
- 业务角色与权限。
- 前置条件。
- 业务输入与输出。
- 正常业务流程。
- 业务规则与业务状态变化。
- 业务边界。
- 业务异常情况。
- 架构与技术约束。
- 模块职责与依赖。
- 数据来源、责任归属、读写方向与一致性边界。
- 代码行为要求。
- 范围取舍与非目标。
- 明确禁止的业务行为。
- 可验证的验收条件。

不适用的章节必须保留并写明“不适用”及原因。

## 前置条件

前置条件是在当前设计的功能开始之前，已经由其他责任方保证成立的事实。每项前置条件必须说明保证方或关联设计，以及当前设计从哪个已满足状态开始。

| 前置条件 | 保证方或关联设计 | 当前设计的起点 |
| -------- | ---------------- | -------------- |

当前设计必须无条件假设已声明的前置条件成立：

- 不验证前置条件；
- 不重新获取或建立前置条件；
- 不设计前置条件失败、超时或缺失时的业务结果；
- 不增加重试、兜底、默认值、跳转、恢复或捕获；
- 不把前置条件不满足列为当前功能的业务异常或验收场景。

前置条件不满足属于保证方或系统集成缺陷，失败应自然上抛。当前模块负责验证的外部输入、权限、安全边界或业务状态不是前置条件，仍必须在当前详细设计中规定。

## 模块职责与跨模块边界

详细设计只能定义当前文档所属模块的业务、架构、技术和代码行为。可以在“模块职责与依赖”中说明当前模块需要其他模块提供的边界能力、稳定契约或前置保证，但不得设计对方模块的功能、内部结构、技术选择、数据、异常或代码。

发现其他模块必须变更时，当前详细设计的受影响范围必须保持 `草案` 或 `待确认` 并停止展开。在当前会话中报告目标模块、所需能力、阻塞原因和影响范围，取得用户决定后切换到目标模块自己的详细设计处理。不得在当前详细设计中增加临时“变更请求”章节，也不得把尚未确认的目标模块能力写成已经成立的前置条件。

目标模块完成设计、实施和代码并形成有效保证后，当前详细设计才能引用该保证并继续确认。目标模块的实现方式不在当前详细设计中重复描述。

## 数据来源与流向

详细设计必须预定所有跨模块、组件、路由、进程、存储或信任边界的数据流。这里的数据包括持久化记录、接口输入输出、路由状态、临时草稿、派生数据、缓存、事件和消息，不得只描述数据库表。

至少使用下表或等价的可检索结构说明：

| 数据或信息 | 权威来源 | 产生或维护模块 | 消费模块 | 允许的读写方向 | 一致性、生命周期与安全边界 |
| ---------- | -------- | -------------- | -------- | -------------- | -------------------------- |

- 权威来源表示发生冲突时以谁为准；产生或维护模块表示谁对其语义负责，两者不得用模糊的“前端共享状态”替代。
- 必须区分持久化事实、请求结果、可恢复的导航状态、组件生命周期内的临时草稿和纯派生值。
- 写入必须经过被设计的责任模块；消费方不能因能够访问数据就获得修改权。
- 复制、缓存或多入口写入只有在必要性、一致性策略和失效边界已经确定时才允许。
- 本层确定架构方向和责任边界，不展开具体文件、变量、响应式容器或函数调用；这些内容由实施文档锁定。

数据经过三个及以上责任模块，或跨越持久化、远程系统、安全信任边界时，必须同时提供数据流图或时序图。即使使用图表，权威来源、读写方向和一致性结论仍须以文字或表格给出。

## 业务边界与业务异常

业务边界至少说明适用范围、支持和不支持的操作或数据、业务状态限制，以及超出边界时可观察的业务结果。已经声明为前置条件的情况不在本章节重复处理。

业务异常建议按下表表达：

| 业务情况 | 业务结果 | 状态是否变化 | 用户后续操作 | 验收方式 |
| -------- | -------- | ------------ | ------------ | -------- |

不得为了业务异常机械设计 `Error`、异常类、错误码或捕获分支。例如，录入缺勤和录入正常出勤可以是同一个成功业务操作，只写入不同的业务状态。

## 范围取舍、明确禁止与涌现能力

详细设计必须区分以下内容：

- `暂不提供`：本期不建设专用能力，也不承诺交付。
- `不保证兼容`：不进行专项验证、测试或维护，可能偶然可用。
- `明确禁止`：业务上不允许发生，必须规定禁止原因、用户可观察结果、状态是否变化和验收方式。

不得单独使用含义不明的“不支持”。“暂不提供”和“不保证兼容”只限定产品承诺，不授权实施文档增加检测、拒绝或破坏逻辑；已经存在的通用能力不应仅因某种组合用途处于范围外而被主动限制。明确禁止才是实施文档设计业务阻断的依据。

范围取舍建议按下表表达：

| 事项 | 分类 | 本期产品承诺 | 对现有通用能力的影响 |
| ---- | ---- | ------------ | -------------------- |

明确禁止的业务行为建议按下表表达；没有明确禁止事项时写明“不适用”：

| 行为 | 禁止原因 | 用户可观察结果 | 状态变化 | 验收方式 |
| ---- | -------- | -------------- | -------- | -------- |

不可预测的涌现能力不要求识别、列举或写入详细设计。未写入不代表禁止，也不形成稳定性或兼容性承诺；只有决定正式支持或明确禁止时，才按照正常设计流程纳入文档。

## 架构、技术与代码行为

详细设计可以根据方案评审需要明确规定：

- 架构分层、模块职责、组件边界和依赖方向；
- 必须采用或禁止采用的技术、框架、协议和设计模式；
- 接口行为、状态码、错误类型和传播原则；
- 数据模型原则、约束、事务、一致性和迁移要求；
- 超时、重试、并发、安全、日志、监控和部署要求；
- 为保证方案成立而必须出现或不得出现的具体代码行为。

技术术语必须准确，必要时解释其设计意图和取舍。详细设计可以引用稳定的模块或代码位置，但具体新增、修改哪些文件和符号、按什么顺序编码以及如何逐项验证，应由实施文档展开。

## 专业图表

详细设计应优先使用专业的业务图表或架构图表表达设计。只有功能模块比较简单，并且文字描述比图表更简洁、清晰时，才可以省略图表。可以使用的图表包括：

| 图表类型             | 适用场景                                       | Markdown 表达方式         |
| -------------------- | ---------------------------------------------- | ------------------------- |
| 业务流程图           | 存在多个业务步骤、判断或分支                   | Mermaid `flowchart`       |
| 用户旅程图           | 需要表达用户在不同阶段的目标、行为和结果       | Mermaid `journey`         |
| 业务状态图           | 业务对象存在明确状态及转换条件                 | Mermaid `stateDiagram-v2` |
| 生命周期图           | 业务对象具有创建、启用、暂停或结束等阶段       | Mermaid `stateDiagram-v2` |
| 决策树               | 业务结果取决于多个连续判断                     | Mermaid `flowchart`       |
| 业务规则决策表       | 多个条件组合决定业务结果，流程图会产生过多分支 | Markdown 表格             |
| 业务概念关系图       | 需要解释业务概念及其关系，但不定义数据库结构   | Mermaid `flowchart`       |
| 业务异常与恢复流程图 | 业务异常包含多步恢复操作或状态变化             | Mermaid `flowchart`       |
| 系统上下文图         | 需要审核系统与外部参与者或系统的边界           | Mermaid `flowchart`       |
| 模块关系图           | 需要审核运行单元、模块职责和依赖方向           | Mermaid `flowchart`       |
| 接口时序图           | 需要审核跨模块调用顺序和责任归属               | Mermaid `sequenceDiagram` |
| 数据流或信任边界图   | 需要审核数据路径、安全边界和技术约束           | Mermaid `flowchart` 子图  |

业务图表应使用业务角色、业务动作、业务信息和业务状态命名；架构图表可以使用准确的技术术语。图表应支持方案评审，不得把逐文件编码步骤塞入详细设计。

## 完整性与确认

进入 `已确认` 前必须确认：

- 目标、角色、输入输出和业务规则不存在需要下游猜测的缺口；
- 每项前置条件都有明确保证方，当前设计没有重复验证、处理或捕获前置条件失败；
- 当前文档只设计所属模块，跨模块需求已经由目标模块自己的文档承接，没有越界设计或假设尚未成立的契约；
- 正常流程、业务边界和业务异常结果一致；
- 架构、模块职责、技术约束和代码行为要求足以约束实施方案；
- 每项跨边界数据都有明确权威来源、责任模块、消费者、读写方向和一致性边界，实施者无需自行决定数据所有权；
- 验收条件可观察、可判定，不使用“正确处理”“体验良好”等模糊描述；
- 范围取舍和明确禁止不存在混淆，范围外事项没有被表述成必须阻断；
- 业务决策与技术方案相互一致，没有用技术细节掩盖未完成的业务决策；
- 实施文档可以在不重新选择架构或补造设计决策的情况下展开具体编码步骤。
